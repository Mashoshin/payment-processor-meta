# Cross-review

Вход: путь к тикету в `tickets/in-progress/` с ветками `<ticket-id>`
в worktrees сервисов.

Принцип: **автор не проверяет себя.** Ревью делает субагент, не участвовавший
в реализации; на каждый затронутый сервис — свой ревьюер, плюс один сводный.

## Шаги

1. Прочитай тикет: подзадачи, изменения контрактов, критерий приёмки.
2. Для каждого затронутого сервиса возьми дифф:
   `git -C workspace/<service>-<ticket-id> diff main...HEAD`
3. Запусти параллельно по субагенту-ревьюеру на сервис. Каждому дай: дифф,
   контракт сервиса, подзадачу, инварианты из `map.md`. Вопросы ревьюеру:
   - Соответствует ли реализация контракту? Каждый path, код ответа, схема.
   - Не нарушены ли инварианты (копейки, формат счетов, формат ошибок)?
   - Не сделано ли лишнего сверх подзадачи? Лишнее — перечислить.
   - Не лезет ли сервис в чужое хранилище или мимо чужого API?
4. Сводный проход (сам или отдельным агентом): согласованы ли изменения
   МЕЖДУ сервисами — то, чего не видит ни один ревьюер по отдельности.
   Пример: payments шлёт поле, которое ledger не принимает; формат сообщения
   уведомления разошёлся между payments и критерием приёмки.
5. Сверь `map.md` и `registry/` с секцией «Влияние на map.md и registry/»
   тикета: заявленные правки документации сделаны, а незаявленных расхождений
   не осталось — изменившееся поведение на границе сервисов, инварианты, роль
   сервиса, список осознанных дыр. Пустая секция при изменившемся контракте —
   замечание, а не норма.
6. Все замечания — в «Журнал» тикета с пометкой severity (blocker / minor).

## Выход

Вердикт: `approve` или `needs-work` со списком блокеров. При `needs-work` —
конкретные замечания по сервисам; их исправление — повторный заход
`/implement-ticket` по тем же worktrees. `/submit-ticket` (создание PR-ов)
разрешён только после `approve` и зелёного `/integration-check`.
