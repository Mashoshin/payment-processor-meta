# Декомпозиция тикета

Вход: путь к тикету в `tickets/open/` (если не указан — спроси).

## Шаги

1. Прочитай тикет, `map.md` и манифесты из `registry/`.
2. Определи затронутые сервисы. Для каждого — одна строка «почему затронут».
   Сервис не затронут — не притягивай его ради симметрии.
3. Для каждого затронутого сервиса прочитай его контракт из `contracts/`
   и определи, меняется ли API. Заполни секцию «Изменения контрактов»
   **конкретными диффами** (какой path, какое поле, какой тип). Контракты
   не меняются — напиши «нет». Тем же заходом заполни «Влияние на map.md
   и registry/»: что в карте и манифестах перестанет быть правдой после
   этого тикета (инварианты, поток платежа, роль сервиса, список осознанных
   дыр). Не затрагивает — напиши «нет».
4. Напиши подзадачи — по одной на затронутый сервис. Требование
   самодостаточности: агент, видящий только подзадачу + контракт + манифест
   своего сервиса, должен суметь реализовать её без вопросов. Проверь каждую
   подзадачу этим критерием.
5. Напиши критерий приёмки — сквозной сценарий из curl-запросов с ожидаемыми
   ответами, включая хотя бы один негативный случай.
6. Запиши всё в файл тикета. Секцию «Журнал» дополни строкой о декомпозиции.

## Ограничения

- Ты только планируешь: код сервисов и файлы контрактов НЕ трогаешь.
  Правки контрактов описываются в тикете, применяются на этапе implement.
- Не выходи за формулировку тикета: «заодно починить» — это отдельный тикет,
  предложи его в журнале.
- Против инвариантов из `map.md` не идти; если тикет им противоречит —
  останови работу и скажи об этом.

## Выход

Обновлённый файл тикета + короткое резюме пользователю: затронутые сервисы,
есть ли правки контрактов, готов ли тикет к утверждению. Тикет в `in-progress/`
переносит человек — это и есть утверждение.
