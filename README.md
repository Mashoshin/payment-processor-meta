# Метарепозиторий платёжной системы

Координационный слой для агентной разработки системы из нескольких
микросервисов. Кода сервисов здесь нет — здесь **знание о системе**
(карта, контракты, манифесты) и **процесс работы с ней** (планы, тикеты,
workflow-скиллы, хуки-ограничители).

Идея: агент, запущенный в этом репозитории (локально или в контейнере),
получает всё необходимое, чтобы вести изменение через несколько сервисов —
от идеи до merge — не разъезжаясь в контрактах и не нарушая границ.

## Система

```
  client
    |
    v
 [payments :8081] --(1) POST /entries--------> [ledger :8082]
    |
    +--------------(2) POST /notify----------> [notifications :8083]
```

| Сервис | Роль | Репозиторий |
|---|---|---|
| payments | оркестратор: приём платежа, проведение потока | [payments-api](https://github.com/Mashoshin/payments-api) |
| ledger | журнал проводок (двойная запись), источник правды о деньгах | [ledger-api](https://github.com/Mashoshin/ledger-api) |
| notifications | уведомления по счетам | [notifications-api](https://github.com/Mashoshin/notifications-api) |

Подробности: [`map.md`](map.md) — связи, поведение при сбоях, инварианты;
[`registry/`](registry/) — манифест каждого сервиса; [`contracts/`](contracts/) —
OpenAPI, **источник правды об API** (код обязан соответствовать контракту,
не наоборот).

## Быстрый старт для разработчика: агент в Docker (рекомендуемый путь)

Мета самодостаточна, поэтому агент запускается в контейнере, где смонтирована
**только она**: файлов хоста (ssh-ключи, соседние проекты, ~/.claude)
в контейнере физически не существует — изоляция границей файловой системы,
а не дисциплиной.

```bash
claude setup-token             # подписка Pro/Max: интерактивно, в конце напечатает sk-ant-oat01-...
export CLAUDE_CODE_OAUTH_TOKEN='sk-ant-oat01-...'   # вставить напечатанный токен
export GH_TOKEN=...            # fine-grained токен ТОЛЬКО на 4 репозитория системы
scripts/claude-docker.sh       # соберёт образ и запустит Claude Code в /work
```

Не заворачивайте `claude setup-token` в `$(...)` — команда интерактивная
(браузер, подтверждение), при подстановке в переменную попадёт пустота
и claude в контейнере снова попросит логин.

Аутентификация — любой из трёх способов: токен подписки
(`claude setup-token` на хосте, рекомендуется), API-ключ, или интерактивный
`/login` внутри контейнера. Первой строкой при старте контейнер печатает,
какой способ он видит (`auth: ...`) — если это не то, что вы ожидали,
проверьте окружение (пустой `ANTHROPIC_API_KEY` перебивал бы токен;
entrypoint такие сбрасывает сам).

Весь дом агента (`/home/agent`) живёт в именованном томе
`metarepo-agent-home`: логин, тема и онбординг (`~/.claude.json`) переживают
перезапуски — тема и браузерный вход спрашиваются максимум один раз.
«Разлогинить» агента: `docker volume rm metarepo-agent-home`. Хостовый
`~/.claude` в контейнер не монтируется принципиально — это была бы дыра
в изоляции.

Внутри образа: PHP 8.4, git, gh, Node 22, Claude Code; пользователь без root.
Дальше — обычный конвейер: `scripts/bootstrap.sh`, `/grill`, тикеты.

Полезное:

- `scripts/claude-docker.sh bash` — шелл в контейнере вместо агента;
- `scripts/claude-docker.sh --build` — пересобрать образ;
- внутри контейнера можно осознанно запустить
  `claude --dangerously-skip-permissions` — без подтверждений на каждый
  инструмент: границей безопасности здесь служит контейнер, а не разрешения
  харнеса. Снаружи контейнера так делать не стоит;
- `GH_TOKEN` выпускайте fine-grained и только на `payment-processor-meta`,
  `payments-api`, `ledger-api`, `notifications-api` — тогда агент физически
  не дотянется до остальных ваших репозиториев;
- проверка границы: попросите агента прочитать `~/.ssh/id_rsa` хоста или
  «показать соседние проекты» — получите `No such file or directory`,
  это и есть доказательство изоляции.

## Быстрый старт без Docker

Требуется PHP 8.3+ и git. Фреймворков и composer-зависимостей нет.

```bash
scripts/bootstrap.sh   # клонирует сервисы в workspace/ по манифестам registry/
scripts/run-all.sh     # поднимает все сервисы; топология (URL соседей)
                       # собирается из манифестов и передаётся через окружение
scripts/smoke.sh       # сквозной smoke-тест: платёж → проводка → уведомление.
                       # Идемпотентен: уникальные счета на каждый прогон
scripts/stop-all.sh    # гасит сервисы
```

`workspace/` — рабочие копии сервисов, в git меты не входят (.gitignore).

## Процесс: от идеи до merge

Человек приносит идею, отвечает на развилки в чате и подтверждает.
Всё остальное — планы, тикеты, декомпозицию, код, ревью — пишут агенты;
файлы руками не правятся.

```
/grill <идея>  — диалог: агент задаёт вопросы по развилкам, спорит,
                 сводка решений, подтверждение в чате
   → /to-plan  — та же сессия: итоги из контекста → план в plans/ (approved)
   → /plan-to-tickets → /decompose-ticket → утверждение (человек)
   → /implement-ticket → /cross-review → /integration-check
   → /submit-ticket — PR на каждый затронутый сервис + PR-«зонтик» в мете
   → ревью и merge PR-ов (человек, на GitHub)
   → /close-ticket — pull main, финальный smoke, тикет в done
```

| Скилл (`.claude/skills/`) | Что делает |
|---|---|
| `/grill <идея>` | интерактивная гриль-сессия: развилки, спор адвоката дьявола — всё в чате |
| `/to-plan` | материализует итоги гриль-сессии из контекста в план `plans/` |
| `/plan-to-tickets` | утверждённый план → тикеты в `tickets/open/` |
| `/decompose-ticket` | тикет → затронутые сервисы, правки контрактов, подзадачи |
| `/implement-ticket` | параллельные субагенты по worktree на каждый затронутый сервис |
| `/cross-review` | независимые ревьюеры: сверка диффов с контрактами и между собой |
| `/integration-check` | запуск всех сервисов + smoke + критерий приёмки тикета |
| `/submit-ticket` | ветки → PR-ы со ссылками в тикете, worktrees убираются |
| `/close-ticket` | после merge PR-ов человеком: pull, финальный smoke, тикет в done |

## Правила и их enforcement

Правила описаны в [`CLAUDE.md`](CLAUDE.md); ключевые подкреплены механизмами,
а не просьбами:

- **Contract-first** — правка `contracts/` без тикета в `tickets/in-progress/`
  блокируется PreToolUse-хуком (`scripts/hooks/contract-guard.sh`);
- **автор не проверяет себя** — ревью выполняют отдельные субагенты;
- **границы сервисов** — агент сервиса X работает только в worktree X,
  чужие сервисы доступны только через их API по контракту;
- **журнал сессий** — каждый промпт человека автоматически пишется
  в `sessions/` хуком UserPromptSubmit (`scripts/hooks/log-prompt.sh`):
  вместе с интерактивным грилем это даёт полную историю решений.

## Структура

```
CLAUDE.md        правила и точка входа для агента
map.md           карта системы: связи, сбои, инварианты, осознанные дыры
registry/        манифесты сервисов (name, repo, port — источник топологии)
contracts/       OpenAPI-контракты — источник правды об API
plans/           планы: draft → approved → converted
tickets/         тикеты: open/ → in-progress/ → review/ → done/
sessions/        журнал промптов (ведётся хуком автоматически)
.claude/skills/  workflow-скиллы (см. таблицу выше)
.claude/settings.json + scripts/hooks/  хуки-ограничители
scripts/         bootstrap / run-all / stop-all / smoke / claude-docker
Dockerfile + docker/  изолированная среда агента (см. «Быстрый старт»)
workspace/       рабочие копии сервисов (не под git)
```

## Как добавить сервис

1. Положить манифест `registry/<name>.md` (name, repo, port, контракт).
2. Положить контракт `contracts/<name>.openapi.yaml`.
3. Дописать сервис в `map.md` (связи, поведение при сбоях).
4. `scripts/bootstrap.sh` — и bootstrap/run-all подхватят его без правки
   скриптов; все сервисы автоматически получат `<NAME>_URL` в окружении.
