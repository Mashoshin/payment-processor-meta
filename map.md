# Карта системы

## Архитектура

```
  client
    |
    v
 [payments :8081] --(1) POST /entries--------> [ledger :8082]
    |
    +--------------(2) POST /notify----------> [notifications :8083]
```

| Сервис | Роль | Зовёт | Кого-то ждёт |
|---|---|---|---|
| payments | оркестратор: приём платежа, проведение потока | ledger, notifications | да |
| ledger | журнал проводок (двойная запись), источник правды о деньгах | никого | нет |
| notifications | хранение и лента уведомлений по счетам | никого | нет |

## Поведение при сбоях (зафиксировано, менять только системным тикетом)

- `ledger` недоступен или ответил не `201` → платёж `failed`, клиенту `502`.
  Проводка **критична**: без неё платежа нет.
- `notifications` недоступен → платёж **успешен**, `notification_sent: false`.
  Уведомление — **best effort**.

## Сквозные инварианты

1. **Деньги** — целые числа в копейках. Никаких float. Валюта v1 — только RUB.
2. **Счета** — строки `^acc_[a-z0-9_]+$`. Реестра счетов нет: любой корректный
   идентификатор — существующий счёт.
3. **Проводки неизменяемы**: только дозапись. Исправление — сторнирующей
   проводкой (в v1 не реализовано).
4. **Баланс** = sum(credit) − sum(debit) по журналу. Отрицательный допустим
   (контроля овердрафта в v1 нет).
5. **Формат ошибок** — `{"error": "<описание>"}`; 400 валидация, 404 не найдено,
   502 сбой зависимости.
6. **Идентификаторы** — префикс типа + случайный суффикс: `pay_`, `ent_`, `ntf_`.

## Известные осознанные дыры (кандидаты в тикеты)

- Повторный `POST /entries` с тем же `payment_id` создаёт дубль проводки —
  идемпотентности нет.
- Комиссий нет.
- Отмены/сторно нет.
- Контроля достаточности средств нет.
