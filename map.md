# Карта системы

## Архитектура

```
  client
    |
    v
 [payments :8081] --(1) POST /entries: 2 проводки атомарно--> [ledger :8082]
    |                      перевод from -> to
    |                      комиссия from -> acc_fee
    |
    +--------------(2) POST /notify-------------------------> [notifications :8083]
```

| Сервис | Роль | Зовёт | Кого-то ждёт |
|---|---|---|---|
| payments | оркестратор: приём платежа, проведение потока | ledger, notifications | да |
| ledger | журнал проводок (двойная запись), источник правды о деньгах | никого | нет |
| notifications | хранение и лента уведомлений по счетам | никого | нет |

Поток одного платежа: payments считает комиссию, одним запросом `POST /entries`
кладёт в ledger **две** проводки — перевод и комиссионное плечо — атомарно
(всё-или-ничего), затем best-effort уведомляет получателя.

## Поведение при сбоях (зафиксировано, менять только системным тикетом)

- `ledger` недоступен или ответил не `201` → платёж `failed`, клиенту `502`.
  Проводка **критична**: без неё платежа нет.
- `notifications` недоступен → платёж **успешен**, `notification_sent: false`.
  Уведомление — **best effort**.

## Повторы и идемпотентность

- Ключ идемпотентности платежа — пара `(from, client_oid)`. `client_oid` задаёт
  клиент, поле обязательное. Тот же `client_oid` от другого отправителя — это
  другой платёж.
- Точный повтор (тот же ключ, те же `to` и `amount`) → `200` и тот же платёж:
  ничего не списывается, проводки не дописываются, уведомление не шлётся
  повторно. Новый платёж — `201`.
- Тот же ключ с другими `to`/`amount` → `409`, при **любом** статусе найденного
  платежа. Ключ освобождается только под точный повтор: повтор после `failed`
  проводит платёж заново, переиспользуя тот же `pay_`-идентификатор, и отдаёт
  `201`.
- `ledger` идемпотентен по `payment_id`: если проводки с таким `payment_id` уже
  есть, ничего не дописывается и возвращаются ранее записанные (`200`). Тело
  повтора не сверяется — `payment_id` единственный ключ.

## Сквозные инварианты

1. **Деньги** — целые числа в копейках. Никаких float. Валюта v1 — только RUB.
   Комиссия удерживается **сверху**: списание с отправителя = `amount + fee`,
   получателю приходит ровно `amount`. Комиссия округляется **вверх** до целой
   копейки, минимум — 1 копейка (перевод в 1 копейку стоит 2). Ставка — параметр
   payments и живёт в `contracts/payments.openapi.yaml`, а не здесь.
2. **Счета** — строки `^acc_[a-z0-9_]+$`. Реестра счетов нет: любой корректный
   идентификатор — существующий счёт. `acc_fee` — системный счёт-накопитель
   комиссии; он выделен только по смыслу, технически это обычный счёт.
3. **Проводки неизменяемы**: только дозапись. Исправление — сторнирующей
   проводкой (в v1 не реализовано).
4. **Баланс** = sum(credit) − sum(debit) по журналу. Отрицательный допустим
   (контроля овердрафта в v1 нет).
5. **Формат ошибок** — `{"error": "<описание>"}`; 400 валидация, 404 не найдено,
   409 конфликт ключа идемпотентности, 502 сбой зависимости.
6. **Идентификаторы** — префикс типа + случайный суффикс: `pay_`, `ent_`, `ntf_`.

## Известные осознанные дыры (кандидаты в тикеты)

- Проверка-и-вставка ключа `(from, client_oid)` в payments не под блокировкой:
  два строго одновременных запроса с одним ключом могут создать два платежа.
  Последовательный повтор закрыт.
- `acc_fee` ничем не защищён: обычный `POST /payments` с `from: acc_fee` уводит
  накопленную комиссию на любой счёт — и удерживает с этого перевода комиссию
  обратно в `acc_fee`.
- Отмены/сторно нет.
- Контроля достаточности средств нет.
