# T-001: Комиссия 1% с каждого перевода

status: review          # open | in-progress | review | done

## Задача

План: plans/P-001-transfer-fee-1pct.md

Система удерживает 1% комиссии с каждого перевода в свою пользу. `amount`
в запросе остаётся суммой получателю: получатель зачисляется ровно на
`amount`, отправитель платит `amount + fee`, комиссия зачисляется на единый
системный счёт `acc_fee`. Ставка 1% — зашитый инвариант v1, минимальная
комиссия 1 копейка (комиссия округляется вверх).

Клиент явно видит размер комиссии и итоговое списание: в ответе перевода
появляются `fee` (копейки) и `total = amount + fee`. Комиссия должна
реально учитываться в деньгах системы как движение в ledger, а не как
декоративное поле в ответе — то есть на каждом переводе в ledger должны
появиться и плечо перевода, и плечо комиссии, и они не должны расходиться
между собой (либо оба записаны, либо ни одного).

### payments

Реализовать удержание комиссии 1% «сверху» в оркестраторе.

Что сделать:
1. При `POST /payments {from, to, amount}` посчитать комиссию:
   `fee = ceil(amount / 100)`, но не меньше 1 копейки. Ставка 1% —
   **зашитая константа** (инвариант v1, не конфиг, не переменная окружения).
   Реализация целочисленная, без float: `fee = intdiv(amount + 99, 100)`
   (для `amount ≥ 1` это даёт округление вверх и минимум 1: 1→1, 55→1,
   100→1, 101→2, 150→2, 10000→100).
2. `total = amount + fee`.
3. Сформировать два плеча и записать их в ledger **одним** запросом
   `POST {LEDGER_URL}/entries` с телом-**массивом** (новый контракт ledger):
   - плечо перевода: `{payment_id, debit: from, credit: to, amount}`
   - плечо комиссии: `{payment_id, debit: from, credit: "acc_fee", amount: fee}`
   `payment_id` — id этого платежа (`pay_...`), одинаковый у обоих плеч.
   Порядок: сначала перевод, затем комиссия.
4. Если ledger ответил `201` — платёж `completed`; иначе (недоступен или
   не `201`) — платёж `failed`, клиенту `502` с телом `{"error": "..."}`
   (поведение при сбоях из `map.md` — не меняется; ledger критичен).
   **Второго запроса в ledger при сбое не делать** — атомарность на стороне
   ledger, «фантома» быть не должно.
5. Уведомление в notifications — как раньше, best-effort, после успешной
   записи в ledger; на `fee`/`total` не влияет. Поток и содержимое не меняем.
6. В ответе `Payment` (и в `GET /payments/{id}`) добавить поля `fee`
   (копейки) и `total = amount + fee`. Остальные поля без изменений.

Границы: комиссия целыми копейками, без float; счёт комиссии — строго
`acc_fee`; чужие хранилища (`var/` ledger/notifications) не трогать — только
через их API. Правку `contracts/payments.openapi.yaml` (поля `fee`, `total`)
и вызов нового массива ledger применяет этот же агент в своём worktree.

### ledger

Сделать `POST /entries` атомарной записью массива проводок (ломающее).

Что сделать:
1. Тело запроса теперь **массив** объектов проводок (не одиночный объект),
   длина 1..2. Каждый элемент: `{payment_id, debit, credit, amount}` — те же
   правила валидации, что и раньше для одной проводки.
2. Провалидировать **все** элементы до записи: формат счетов
   (`^acc_[a-z0-9_]+$`), `debit != credit`, `amount >= 1` (целое, копейки),
   `payment_id` непустой. Массив пуст или длиннее 2 → `400`.
3. **Атомарность (всё-или-ничего):** если хоть один элемент невалиден —
   вернуть `400 {"error": "..."}` и **не дописывать в журнал ничего**
   (ни первого плеча). Дозаписывать частично запрещено.
4. При успехе записать все проводки (в порядке массива), каждой присвоить
   `id` (`ent_...`) и `created_at`, вернуть `201` с телом-**массивом**
   `Entry` в том же порядке.
5. Идемпотентности по `payment_id` по-прежнему НЕТ — повтор всего запроса
   создаёт дубль обоих плеч (осознанная дыра, D8, вне скоупа).
6. `GET /accounts/{id}/balance` и `GET /health` — без изменений. Баланс
   по-прежнему `sum(credit) − sum(debit)` по всем проводкам журнала;
   `acc_fee` — обычный счёт, отдельной логики не требует.

Границы: ledger никого не зовёт и ни о ком не знает — про «комиссию»,
«payments» и `acc_fee` ничего специального знать не должен, это просто ещё
одна проводка. Правку `contracts/ledger.openapi.yaml` (массив в запросе и
ответе, схема `EntryInput`) применяет этот же агент в своём worktree.

## Критерий приёмки

<!-- черновик сквозного сценария; детализирует /decompose-ticket -->

Предполагается: сервисы подняты (`scripts/run-all.sh`), payments :8081,
ledger :8082. Счета берём «чистые» под прогон.

**1. Перевод на круглую сумму + два плеча в ledger.**

```bash
curl -s -X POST localhost:8081/payments \
  -H 'Content-Type: application/json' \
  -d '{"from":"acc_alice","to":"acc_bob","amount":10000}'
```
Ожидаем `201`, тело содержит `"amount":10000, "fee":100, "total":10100`,
`"status":"completed"`. Пусть id ответа — `$PAY`.

Проверка проводок через баланс (до прогона счета пустые):
```bash
curl -s localhost:8082/accounts/acc_bob/balance     # balance: +10000 (credit перевода)
curl -s localhost:8082/accounts/acc_fee/balance     # balance: +100   (credit комиссии)
curl -s localhost:8082/accounts/acc_alice/balance   # balance: -10100 (debit обоих плеч), entries_count: 2
```
`acc_alice` дебетован ровно на `total`; сумма кредитов (`acc_bob` +
`acc_fee`) = `total`. Ровно две проводки по платежу, оба с `debit=acc_alice`.

**2. Округление вверх / минимум 1 копейка.**

```bash
curl -s -X POST localhost:8081/payments -H 'Content-Type: application/json' \
  -d '{"from":"acc_x","to":"acc_y","amount":55}'    # fee=1,  total=56
curl -s -X POST localhost:8081/payments -H 'Content-Type: application/json' \
  -d '{"from":"acc_x","to":"acc_y","amount":150}'   # fee=2,  total=152
curl -s -X POST localhost:8081/payments -H 'Content-Type: application/json' \
  -d '{"from":"acc_x","to":"acc_y","amount":1}'     # fee=1,  total=2
```

**3. Негативный случай — атомарность при сбое ledger (нет «фантома»).**

Симулировать недоступность ledger (погасить процесс ledger или указать
payments битый `LEDGER_URL`), затем:
```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8081/payments \
  -H 'Content-Type: application/json' \
  -d '{"from":"acc_p","to":"acc_q","amount":10000}'   # ожидаем 502
```
Тело — `{"error": "..."}`; платёж сохранён со `status:"failed"`
(`GET /payments/{id}`). После поднятия ledger:
```bash
curl -s localhost:8082/accounts/acc_p/balance   # balance: 0, entries_count: 0 — ни одного плеча
curl -s localhost:8082/accounts/acc_q/balance   # balance: 0
```
Ни одиночного плеча перевода, ни одиночного плеча комиссии в журнале нет.

**4. Негативный случай — валидация на границе (без изменений).**

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8081/payments \
  -H 'Content-Type: application/json' \
  -d '{"from":"acc_a","to":"acc_a","amount":100}'   # 400 (from==to)
```

- Вне скоупа (не проверяется этим тикетом): идемпотентность — повторный
  запрос по-прежнему создаёт дубль обоих плеч (известная дыра, отдельный
  системный тикет).
