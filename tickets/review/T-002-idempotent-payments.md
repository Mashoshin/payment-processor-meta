# T-002: Идемпотентность платежей по клиентскому ключу

status: review            # open | in-progress | review | done
created: 2026-09-02
author: e.mashoshin

## Задача

План: plans/P-002-idempotent-payments.md

Повторный запрос на перевод не должен приводить к повторному списанию денег.
Сегодня приводит: у запроса клиента нет никакого идентификатора, поэтому
каждый ретрай после потери ответа или двойного клика — это новый платёж
и новый комплект проводок. Отдельно та же беда этажом ниже: если проводки
в журнал записаны, а ответ до оркестратора не дошёл, повтор запишет их второй раз.

Клиент получает возможность безопасно повторять запрос. Для этого он передаёт
вместе с переводом собственный идентификатор операции — `client_oid`. Поле
обязательное: без него идемпотентность была бы необязательной, то есть
фикцией. Идентификатор принадлежит отправителю: одинаковый `client_oid` от
разных отправителей — это разные переводы, и увидеть чужой платёж по чужому
ключу нельзя.

Поведение при повторе:

- тот же отправитель, тот же `client_oid`, те же получатель и сумма —
  клиенту возвращается **исходный платёж**, а не новый; денег со счёта
  не уходит, проводок в журнале не прибавляется, уведомление повторно
  не отправляется. Если исходный платёж ещё в обработке, клиент видит его
  в этом статусе и может дождаться исхода;
- тот же `client_oid`, но получатель или сумма другие — это ошибка клиента
  («перевод с таким идентификатором уже существует»), а не молчаливый
  возврат чужого перевода: иначе клиент решил бы, что перевёл одну сумму,
  а ушла бы другая;
- исходный перевод завершился неудачей — идентификатор освобождается,
  и клиент вправе повторить. Это главный сценарий: ретрай после отказа —
  нормальное поведение клиента, и запирать его навсегда нельзя. При таком
  повторе система переиспользует прежний идентификатор платежа, чтобы
  журнал узнал уже записанные проводки и не создал их второй раз.

Отдельно и обязательно: журнал проводок перестаёт дублировать записи при
повторе того же платежа — повтор возвращает ранее записанные проводки,
ничего не дописывая. Это закрывает дыру, прямо перечисленную в `map.md`
(«Повторный `POST /entries` с тем же `payment_id` создаёт дубль проводки»),
и без неё описанное выше поведение при ретрае после неудачи не работает.

Вне скоупа: защита от **одновременных** (параллельных) запросов с одним
ключом — проверка-и-вставка ключа в payments не под блокировкой, и двойной
клик, пришедший строго параллельно, всё ещё способен создать два платежа.
Последовательный повтор закрыт полностью. Принято сознательно (P-002, D8),
отдельным тикетом.

### payments

Реализовать идемпотентность платежей по клиентскому ключу `client_oid`.

Что сделать:

1. **Приём и валидация ключа.** `POST /payments` теперь принимает
   обязательное поле `client_oid` — строка по маске `^[A-Za-z0-9_-]{1,64}$`.
   Отсутствует, не строка, пустая или не проходит маску → `400
   {"error": "..."}`, ничего не создаётся. Валидацию `client_oid` делать
   вместе с остальной валидацией входа (`from`/`to`/`amount`), до любых
   побочных эффектов.

2. **Ключ идемпотентности — пара `(from, client_oid)`.** Не один
   `client_oid`: одинаковый ключ от разных отправителей — разные платежи.
   Поиск существующего платежа вести строго по обоим полям.

3. **Хранение.** `client_oid` сохраняется вместе с платежом в
   `var/storage.json` и возвращается в теле `Payment` (и в
   `GET /payments/{id}`).

4. **Ветвление при найденном платеже** по паре `(from, client_oid)`:

   | Найденный платёж | `to` и `amount` запроса | Ответ |
   |---|---|---|
   | `completed` | совпали | `200` + найденный платёж, ничего не делать |
   | `pending` | совпали | `200` + найденный платёж в статусе `pending`, ничего не делать |
   | `failed` | совпали | провести заново — см. п. 5 |
   | любой статус | разошёлся `to` или `amount` | `409 {"error": "..."}` |

   Сверяются ровно два поля: `to` и `amount` (`from` уже часть ключа).
   Расхождение даёт `409` **при любом** статусе найденного платежа,
   включая `failed`: ключ освобождается только под точный повтор.
   Ни `200`, ни `409` не порождают ни проводок, ни уведомлений.

5. **Повтор после `failed` — переиспользовать прежний `pay_id`.** Новый
   идентификатор не генерировать: запись существующего платежа
   обновляется на месте. `id` и `created_at` сохраняются прежними,
   `status` переводится в `pending` и далее по обычному потоку
   (`completed`/`failed`). Это принципиально: ledger дедуплицирует по
   `payment_id`, и только совпадение идентификатора не даёт записать
   второй комплект проводок, если в прошлый раз ledger успел их записать,
   а ответ до payments не дошёл.

6. **Новая пара `(from, client_oid)`** — обычный поток без изменений:
   генерируется новый `pay_id`, считается `fee = ceil(amount/100)` и
   `total = amount + fee`, оба плеча одним массивом уходят в
   `POST {LEDGER_URL}/entries`, при успехе — уведомление best-effort,
   ответ `201`.

7. **Обработка ответа ledger.** Ledger теперь может ответить `200`
   (проводки под этим `payment_id` уже были записаны) вместо `201`.
   **`200` считать успехом наравне с `201`**: платёж `completed`, ответ
   клиенту `201`. Любой другой исход (недоступен, `4xx`, `5xx`) — платёж
   `failed`, клиенту `502` (поведение из `map.md`, не меняется).

8. **Уведомление** — как раньше: best-effort, после успешной записи
   в ledger, влияет только на `notification_sent`. При ответе `200`
   на повтор (п. 4) вызов `/notify` не делается вовсе.

Границы: гонку не чинить — параллельные запросы с одним ключом вне скоупа
(D8, отдельный тикет), блокировку файла не вводить. Формат ошибок строго
`{"error": "<описание>"}` — поля `payment_id` в тело `409` не добавлять
(инвариант 5 `map.md`). Комиссию, расчёт `fee`/`total` и поток плеч из T-001
не менять. Чужие хранилища (`var/` ledger и notifications) не трогать —
только через их API. Файлы `contracts/` не править: контракты уже применены
оркестратором до старта. Обновить `CLAUDE.md` репозитория payments: раздел
«Границы (вне скоупа v1)» числит идемпотентность повторов вне скоупа, а
раздел про `POST /payments` не знает про `client_oid`, коды `200`/`409`
и обязательность ключа.

### ledger

Сделать `POST /entries` идемпотентным по `payment_id`.

Что сделать:

1. **Ключ дедупа — `payment_id`** из элементов входного массива. Если
   хотя бы один `payment_id` запроса уже присутствует в журнале, запрос
   считается повтором.

2. **Поведение при повторе:** в журнал **не дописывать ничего**, вернуть
   `200` с массивом ранее записанных проводок по этим `payment_id`,
   с теми же `id` (`ent_...`) и `created_at`, в порядке их записи
   в журнале. Тело ответа — тот же массив `Entry`, что и у `201`.

3. **Содержимое повторного запроса не сверять.** `payment_id` —
   единственный ключ; расхождение по `debit`/`credit`/`amount` не проверяется
   и ошибкой не является. Сверку параметров делает payments на своей стороне,
   ledger остаётся тупым журналом.

4. **Порядок операций:** сначала обычная валидация всех элементов (формат
   счетов, `debit != credit`, `amount >= 1` целое, `payment_id` непустой,
   длина массива 1..2) — невалидный вход даёт `400` и раньше проверки
   на повтор. Затем проверка на повтор. Затем атомарная запись.

5. **Проверка-и-запись под одной блокировкой.** `Storage` уже пишет под
   `flock` — проверка «есть ли такой `payment_id`» и дозапись проводок
   должны выполняться внутри **того же** захвата блокировки, иначе два
   одновременных запроса с одинаковым `payment_id` оба увидят пустой
   журнал и оба запишут. Разрывать на «прочитать → отпустить → записать»
   нельзя.

6. **Новый `payment_id`** — поведение полностью прежнее: атомарная запись
   всех переданных проводок (всё-или-ничего), `201` с массивом `Entry`
   в том же порядке.

7. `GET /accounts/{id}/balance` и `GET /health` — без изменений.

Границы: ledger по-прежнему никого не зовёт и ничего не знает про платежи,
комиссии и `acc_fee`. Сторно и удаление проводок не появляются — проводки
остаются неизменяемыми, дозапись только. Файлы `contracts/` не править:
контракт уже применён оркестратором до старта. Обновить
`CLAUDE.md` репозитория ledger — раздел «Границы (вне скоупа v1)» сейчас
утверждает, что идемпотентности по `payment_id` нет; это перестаёт быть
правдой.

### notifications

Не затронут. Изменений нет.

## Критерий приёмки

Предполагается: сервисы подняты (`scripts/run-all.sh`), payments :8081,
ledger :8082, notifications :8083. Счета берём «чистые» под прогон.
Комиссия 1% из T-001 действует: `fee = ceil(amount/100)`, `total = amount + fee`.

**1. Обычный перевод с ключом.**

```bash
curl -s -X POST localhost:8081/payments -H 'Content-Type: application/json' \
  -d '{"from":"acc_alice","to":"acc_bob","amount":10000,"client_oid":"order-42"}'
```
Ожидаем `201`, `"status":"completed"`, `"fee":100`, `"total":10100`,
в теле есть `"client_oid":"order-42"`. Пусть id ответа — `$PAY`.

```bash
curl -s localhost:8082/accounts/acc_bob/balance     # balance: +10000
curl -s localhost:8082/accounts/acc_fee/balance     # +100 (дельта)
curl -s localhost:8082/accounts/acc_alice/balance   # balance: -10100, entries_count: 2
curl -s localhost:8083/notifications/acc_bob        # ровно одно уведомление
curl -s localhost:8081/payments/$PAY                # 200, client_oid на месте
```

**2. Точный повтор — исходный платёж, денег не уходит.**

Тот же запрос слово в слово ещё раз. Ожидаем **`200`** (не `201`), в теле —
тот же `id` (`$PAY`), тот же `status: completed`, тот же `client_oid`.

Ничего не изменилось:
```bash
curl -s localhost:8082/accounts/acc_alice/balance   # -10100, entries_count: 2 (не 4)
curl -s localhost:8082/accounts/acc_bob/balance     # +10000
curl -s localhost:8083/notifications/acc_bob        # по-прежнему одно уведомление
```
Отсутствие второго уведомления проверяется отдельно: повтор не должен
доходить до вызова `/notify`.

**3. Тот же ключ, другие параметры — `409`.**

```bash
# другая сумма
curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8081/payments \
  -H 'Content-Type: application/json' \
  -d '{"from":"acc_alice","to":"acc_bob","amount":50000,"client_oid":"order-42"}'
# другой получатель
curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8081/payments \
  -H 'Content-Type: application/json' \
  -d '{"from":"acc_alice","to":"acc_carol","amount":10000,"client_oid":"order-42"}'
```
Оба — `409`, тело `{"error": "..."}`. Балансы `acc_alice`, `acc_bob`
и `acc_carol` не изменились, `entries_count` у `acc_alice` по-прежнему 2.

**4. Тот же ключ от другого отправителя — это другой перевод.**

```bash
curl -s -X POST localhost:8081/payments -H 'Content-Type: application/json' \
  -d '{"from":"acc_dave","to":"acc_bob","amount":10000,"client_oid":"order-42"}'
```
Ожидаем `201` и **новый** `id`, отличный от `$PAY`; в теле `from` —
`acc_dave`. Чужой платёж по чужому ключу не виден.

**5. Валидация ключа — всё `400`, тело `{"error": "..."}`.**

```bash
# ключа нет вовсе
curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8081/payments \
  -H 'Content-Type: application/json' \
  -d '{"from":"acc_a","to":"acc_b","amount":100}'
# пустой ключ
... -d '{"from":"acc_a","to":"acc_b","amount":100,"client_oid":""}'
# недопустимые символы (пробел, восклицательный знак)
... -d '{"from":"acc_a","to":"acc_b","amount":100,"client_oid":"order 42!"}'
# 65 символов — на один больше предела
... -d '{"from":"acc_a","to":"acc_b","amount":100,"client_oid":"aaaa…(65)"}'
```
Граничный случай: ровно 64 символа — валиден, `201`.
Ни один из отклонённых запросов не создаёт платежа и не пишет проводок.

**6. Ретрай после неудачи — ключ освобождён, двойной проводки нет.**

Погасить ledger (или указать payments битый `LEDGER_URL`), затем:
```bash
curl -s -X POST localhost:8081/payments -H 'Content-Type: application/json' \
  -d '{"from":"acc_p","to":"acc_q","amount":10000,"client_oid":"retry-1"}'   # 502
```
Платёж сохранён со `status:"failed"`, его id — `$FAILED`
(`GET /payments/$FAILED` → `200`).

Поднять ledger, повторить тот же запрос слово в слово: ожидаем `201`,
`"status":"completed"`, и `id` — **тот же** `$FAILED` (идентификатор
переиспользован, новый платёж не заведён).

```bash
curl -s localhost:8082/accounts/acc_q/balance   # +10000
curl -s localhost:8082/accounts/acc_p/balance   # -10100, entries_count: 2 (один комплект)
```

**7. Ключ занят даже неудачным платежом, если параметры разошлись.**

После шага 6 (платёж по ключу `retry-1` теперь `completed`) и по аналогии
для `failed`: запрос с тем же `(from, client_oid)`, но другой суммой →
`409`. Ключ освобождается только под точный повтор.

**8. Журнал не дублирует проводки — прямая проверка ledger.**

```bash
curl -s -X POST localhost:8082/entries -H 'Content-Type: application/json' \
  -d '[{"payment_id":"pay_dedup1","debit":"acc_m","credit":"acc_n","amount":10000},
       {"payment_id":"pay_dedup1","debit":"acc_m","credit":"acc_fee","amount":100}]'
```
Первый раз — `201`, две проводки, у каждой свой `ent_...`. Тот же запрос
второй раз — **`200`** и **те же две проводки с теми же `ent_` id**
и теми же `created_at`.

```bash
curl -s localhost:8082/accounts/acc_n/balance   # +10000
curl -s localhost:8082/accounts/acc_m/balance   # -10100, entries_count: 2 (не 4)
```

Негативный случай на границе дедупа и валидации: тот же `payment_id`,
но заведомо невалидное тело (`debit == credit`) → `400`, а **не** `200`;
валидация идёт раньше проверки на повтор, в журнал ничего не дописано.

**9. Регресс — поведение T-001 не сломано.**

С валидным `client_oid` в каждом запросе: `from == to` → `400`;
`amount: 0` → `400`; `amount: 55` → `fee: 1`, `total: 56`;
`amount: 150` → `fee: 2`, `total: 152`.

- Вне скоупа (не проверяется этим тикетом): параллельная гонка — два строго
  одновременных запроса с одним `client_oid` в payments (D8, отдельный
  тикет). В ledger гонки нет: проверка и запись идут под общим `flock`.
